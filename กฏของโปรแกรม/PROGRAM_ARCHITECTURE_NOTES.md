# แผนที่โปรแกรมสำหรับคนและ AI ที่มาแก้ภายหลัง

> เอกสารนี้เป็น Developer Note ไม่แสดงในหน้าจอโปรแกรม  
> ก่อนเปลี่ยน logic ให้ค้นหาหัวข้อ `SECTION NOTE` ใน `snapgen_gui_v2.py`

## กฎความเป็นระเบียบของโฟลเดอร์หลัก

- หน้าโฟลเดอร์หลักต้องแสดงโฟลเดอร์งาน `export` และไฟล์ใช้งาน 3 รายการ: `setup_and_run.bat`, `snapgen_gui_v2.py`, `Tidmunz Studio.lnk`
- `export` เป็นงานผู้ใช้ ต้องมองเห็นเสมอ ห้ามซ่อน ห้ามลบ และห้ามย้ายระหว่างการจัดโฟลเดอร์
- ไฟล์เอกสารต้องอยู่ใน `docs`; เครื่องมือและสคริปต์ดูแลระบบต้องอยู่ใน `tools`
- ห้ามวาง log, dump, debug output, ไฟล์ทดสอบ, ZIP ติดตั้งชั่วคราว หรือผลทดลองไว้ในโฟลเดอร์หลัก
- ผลทดลองต้องลบเมื่อทดสอบเสร็จ ห้ามสะสม `test_artifacts` หรือโมดูลทดลองที่โปรแกรมไม่ได้เรียกใช้
- ไฟล์ที่ไม่ได้ใช้จริงต้องลบ ไม่เก็บเผื่ออนาคต; หากจำเป็นต้องเพิ่มไฟล์ใหม่ ให้ใส่ในโฟลเดอร์ที่ตรงหน้าที่
- ห้ามลบหรือย้ายไฟล์เพียงเพราะดูรกจนกว่าจะตรวจการอ้างอิงและยืนยันว่าโปรแกรมไม่ใช้งาน

## กฎสำคัญที่สุด

1. อย่าเดา business logic จากชื่อฟังก์ชันเพียงอย่างเดียว
2. แยก “ทำความสะอาดไฟล์” ออกจาก “เปลี่ยนพฤติกรรมโปรแกรม”
3. หากจะเปลี่ยน Bridge, GPT, Tailscale, Restore, Update หรือ Account ต้องอ่าน
   เอกสารเฉพาะส่วนนั้นและขอคำสั่งจากเจ้าของก่อน
4. ห้ามลบไฟล์เพราะเห็นว่า import น้อย ต้องตรวจการเรียกผ่าน bytecode,
   `globals()`, callback และ dynamic import ก่อน
5. ห้ามแตะ `export` หรือข้อมูลผู้ใช้ระหว่าง Update/Restore

## 1. การเริ่มโปรแกรม

ไฟล์หลักที่เปิดคือ `snapgen_gui_v2.py`

หน้าที่ช่วงต้นไฟล์:

- ตรวจและใช้ Python ของ `.venv312`
- จัดตำแหน่งโฟลเดอร์เก่าให้เข้ารูปแบบปัจจุบัน
- ตรวจ Bridge และเปิด Bridge เมื่อจำเป็น
- โหลดแกนโปรแกรมจาก `__pycache__/snapgen_core.cpython-312.pyc`
- ติดตั้ง patch/UI adapters เพิ่มจาก source ด้านล่าง

ไฟล์ `.pyc` เป็นส่วนสำคัญของโปรแกรม ไม่ใช่ cache ธรรมดาที่ลบได้

## 2. Bridge, GPT และ Tailscale

อ่านรายละเอียดทั้งหมดที่ `กฏของโปรแกรม/BRIDGE_TEAM_ARCHITECTURE.md`

สรุป:

```text
แต่ละเครื่อง → SnapGen ของตัวเอง → Bridge ของตัวเอง → GPT บัญชีเดียวกัน
```

ทุกเครื่องใช้ Tailscale บัญชี/เครือข่ายเดียวกัน แต่ไม่มี Central Bridge

ค่าที่ต้องแยกให้ออก:

```text
SnapGen ติดต่อ Bridge       = 127.0.0.1
Bridge process เปิดบริการ   = 0.0.0.0
```

ห้ามเปลี่ยนสองค่านี้จากการคาดเดา

## 3. Restore — มีปุ่มเดียว

ใน Settings มีปุ่มชื่อ `Restore` เพียงปุ่มเดียว

หน้าที่:

1. ดึงรายการเวอร์ชันที่เผยแพร่ไว้ใน GitHub Releases
2. ให้ผู้ใช้เลือกเวอร์ชันที่ต้องการ
3. ดาวน์โหลด `tidmun-studio-patch.zip`
4. ตรวจ SHA-256 ของไฟล์ทุกตัวจาก manifest
5. เปลี่ยนเฉพาะไฟล์ตัวโปรแกรมที่อนุญาต
6. ปิดและเปิดโปรแกรมใหม่

Restore ใช้ได้ทั้งย้อนกลับรุ่นเก่าและติดตั้งรุ่นที่เลือก

Restore ไม่ใช่ Backup และต้องไม่แตะ:

- `export`
- รูปหรือวิดีโอของผู้ใช้
- GPT accounts/cookies
- Chrome profile
- การตั้งค่าหรือข้อมูล runtime ใน `snapgen_data`

ตำแหน่งสำคัญ:

- ปุ่มและหน้าต่างเลือกเวอร์ชัน: `run_restore()` ใน `snapgen_gui_v2.py`
- รายการ Release และการดาวน์โหลด: `snapgen_modules/snapgen_updater.py`
- การสร้าง Patch: `tools/build_update_patch.py`
- การเผยแพร่เวอร์ชัน: `tools/publish_update.ps1`

ห้ามสร้างปุ่ม Restore ตัวที่สอง และห้ามนำ Local Backup/ZIP Restore เก่ากลับมา

## 4. Update

Update ต่างจาก Restore ตรงที่ Update เลือกรุ่นล่าสุดให้อัตโนมัติหลังผู้ใช้กด
ตรวจอัปเดต ส่วน Restore ให้ผู้ใช้เลือกเวอร์ชันเอง

ทั้งสองระบบใช้ตัวดาวน์โหลดและตัวติดตั้งเดียวกัน จึงต้องรักษาการตรวจ manifest
และ SHA-256 ไว้เสมอ

## 5. Settings และปุ่มเครื่องมือ

ฟังก์ชัน `_add_settings_maintenance_buttons()` เป็นเจ้าของแถวปุ่มเครื่องมือ
ใน Settings และต้องตรวจปุ่มเดิมก่อนสร้าง เพื่อป้องกันปุ่มซ้ำ

ปุ่มสำคัญในแถวนี้:

- ตรวจและแก้บัค
- ตรวจอัปเดต
- Restore
- ล้าง export
- จับ Account
- อัปขึ้น GitHub เฉพาะเครื่อง Publisher

## 6. Export

`export` คือไฟล์งานของผู้ใช้ ไม่ใช่ไฟล์ตัวโปรแกรม

- Restore และ Update ห้ามลบหรือเขียนทับ
- ปุ่ม `ล้าง export` เป็นคำสั่งแยกและต้องถามยืนยัน
- ห้ามเลือก root drive หรือโฟลเดอร์โปรเจกต์เป็น Export path

### Prop 3D — ผู้ใช้เป็นคนเลือกเครื่องมือ

- ปุ่ม `Hunyuan` ใช้ Hunyuan ตาม logic เดิม
- Flow Hunyuan ต้องใช้ RMBG 2.0 ลบพื้นหลังก่อน เก็บ `background_removed.png` ในโฟลเดอร์งาน และส่ง PNG โปร่งใสนี้เข้า Hunyuan ห้ามส่งรูปต้นฉบับที่ยังมีพื้นหลัง
- ปุ่ม `TripoSplat` ใช้ TripoSplat แล้วแปลง Gaussian Splat เป็น Mesh/GLB
- ปุ่ม `TripoSplat` และ `TRELLIS.2` ต้องตรวจโมเดลของเครื่องนั้นก่อนทุกครั้ง; ถ้ายังไม่ครบให้ติดตั้งอัตโนมัติ แล้วทำงานที่ผู้ใช้กดต่อทันที ไม่บังคับให้ผู้ใช้ทั่วไปเข้าหน้าตั้งค่าเอง
- ห้ามเลือก Hunyuan หรือ TripoSplat แทนผู้ใช้ ผู้ใช้กดอันไหนให้ใช้อันนั้น
- TripoSplat ทำงานผ่าน Python แยกที่ `snapgen_data/tools/triposplat` ห้ามติดตั้ง PyTorch ลง `.venv312` ของโปรแกรมหลัก
- ปุ่ม TripoSplat ห้ามเปิด ComfyUI และห้ามดาวน์โหลดโมเดลเองโดยไม่แจ้งผู้ใช้
- ต้องเก็บไฟล์ Splat/PLY ต้นฉบับไว้ เพราะ Mesh/GLB ที่แปลงแล้วอาจเสียรายละเอียด
- ก่อนเข้า TripoSplat ต้องใช้ `RMBG 2.0` ลบพื้นหลังเป็น PNG โปร่งใสและเก็บ `background_removed.png` ให้ตรวจได้
- หลังลบพื้นหลังต้องปล่อย RMBG 2.0 ออกจาก GPU ก่อนโหลด TripoSplat ห้ามค้างสองโมเดลพร้อมกัน
- น้ำหนัก RMBG 2.0 แบบ self-hosted มีสิทธิ์ CC BY-NC 4.0; การใช้เชิงพาณิชย์ต้องมีข้อตกลงจาก BRIA
- ถ้าเครื่องไม่มี RMBG 2.0 ให้ดาวน์โหลดจาก Google Drive file id `1TSWzo_G5QsNlij4Bg2CNPwUhi-AYjffy` ผ่าน `snapgen_download_rmbg2.py`
- ต้องดาวน์โหลดลง `.part` ก่อน และยอมรับไฟล์เฉพาะขนาด `884878856` bytes กับ SHA-256 `566ed80c3d95f87ada6864d4cbe2290a1c5eb1c7bb0b123e984f60f76b02c3a7`
- ค่า Mesh ต้นทางของ TripoSplat ใช้ resolution `512`; จากนั้น Blender Remesh และลด FBX ให้ไม่เกิน 100,000 faces เพื่อให้เปิดใน iClone เบาลง
- หลังลด TripoSplat ให้ใช้ Laplacian Smooth แบบรักษาปริมาตร (`0.24`, 12 รอบ) เพื่อลบผิวเม็ด/ขรุขระจาก Splat; รายละเอียดสมจริงให้มาจาก BaseColor เป็นหลัก และใช้ Normal strength ต่ำ `0.12` เพื่อไม่ให้จาน/ข้าวดูเป็นหลุม
- TRELLIS.2 ยังใช้ Mesh/UV/PBR เดิมและจำกัดไม่เกิน 850,000 faces; ห้ามนำกฎ 100,000 faces ของ TripoSplatไปใช้กับ TRELLIS.2 หรือ Hunyuan
- ตอนเปลี่ยนตำแหน่ง Export ให้ merge โฟลเดอร์โดยห้ามลบผลลัพธ์เดิมเมื่อชื่อชนกัน; ไฟล์ชื่อซ้ำต้องเก็บทั้งสองชุดหรือเก็บตัวใหม่กว่า ห้ามใช้ `rmtree` กับโฟลเดอร์ปลายทางที่มีงานผู้ใช้
- หลังสร้าง GLB ให้ใช้ Blender แบบ background แปลงเป็น `prop.fbx` พร้อม Vertex Color สำหรับ iClone; ห้ามเปิด Blender UI
- FBX จาก TRELLIS.2 ต้องมีโฟลเดอร์ `prop.fbm` ข้างไฟล์และบันทึก Texture เป็น PNG จริง ห้ามพึ่ง embedded texture เพราะ iClone อาจนำเข้าแล้วเห็นโมเดลไม่มีผิว
- FBX ของ TRELLIS.2 ให้เลียนแบบโครง Hunyuan: `BaseColor.png` แบบ RGB, `Roughness.png` และ `Metallic.png` แบบ grayscale ต่อเข้าช่องตรง, ฝัง Texture ใน FBX และเก็บไฟล์ภายนอกใน `.fbm`; Material ต้อง Opaque
- TripoSplat ไม่มี PBR Texture จากต้นทาง จึงต้อง Bake Vertex Color เป็น `BaseColor.png` หลังลด Mesh แล้ว เพื่อให้ FBX ใช้ใน UE/iClone แบบเดียวกับ Hunyuan
- TripoSplat 850K ต้องสร้าง UV ใหม่และ Bake Base Color ที่ 4096 โดยใช้ island margin `0.0005`; margin กว้างทำให้ชิ้นส่วนจำนวนมากถูกบีบจน Texture เกือบดำ
- ลำดับ TripoSplat ต้องเป็น: สร้าง GLB เต็มตามปกติ → Blender Voxel Remesh จาก Mesh เต็ม → ถ่าย Vertex Color จาก Mesh ต้นฉบับกลับ → Decimate เฉพาะเมื่อยังเกิน 850K → สร้าง UV/Bake Texture → FBX; ห้าม Decimate ก่อน Remesh
- TRELLIS.2/TripoSplat ต้องสร้าง `Normal.png` จากรายละเอียด Base Color สำหรับ Bump; ถ้า TripoSplat ไม่มี PBR ให้สร้าง `Roughness.png` ค่า 0.65 และ `Metallic.png` ค่า 0.0 ห้ามใช้กฎนี้กับ Hunyuan
- FBX จาก TripoSplat จำกัดไม่เกิน 100,000 faces; TRELLIS.2 จำกัดไม่เกิน 850,000 faces; Mesh ที่ต่ำกว่าเพดานของตัวเองอยู่แล้วห้ามลดซ้ำ กฎนี้ห้ามใช้กับ Hunyuan
- ถ้าเครื่องไม่มี Blender ให้เก็บ GLB และแจ้งใน Log ห้ามทำให้งาน TripoSplat ทั้งงานล้ม
- ปุ่ม `TRELLIS.2` ใช้ fork `IgorAherne/TRELLIS.2-stableprojectorz` แบบ local บน Windows ไม่ใช่ `TRELLIS-image-large` รุ่นเก่าและไม่ส่งรูปไปบริการภายนอก
- TRELLIS.2 อยู่แยกที่ `snapgen_data/tools/trellis2`; ห้ามลง PyTorch/CUDA extensions ใน `.venv312` ของ SnapGen
- ค่าเริ่มต้น TRELLIS.2 ใช้ resolution 512, 12 steps, mesh 300,000 faces และ texture 2048 เพื่อให้เสถียรกับ GPU 16GB
- Runner เปิด API เฉพาะ `127.0.0.1:7960`, สร้าง GLB แล้วแปลง FBX ผ่าน Blender background; ถ้า Runner เป็นผู้เปิด API ต้องปิดเมื่อจบเพื่อคืน RAM/VRAM
- ผู้ใช้เป็นคนเลือกเครื่องมือ: กด TRELLIS.2 ต้องใช้ TRELLIS.2 เท่านั้น ห้ามสลับไป Hunyuan หรือ TripoSplat เอง
- หน้า Prop ใช้แถบ Progress 3D เพียงแถบเดียวร่วมกันสำหรับ TripoSplat และ TRELLIS.2; ระหว่างเครื่องมือหนึ่งทำงานต้องปิดปุ่มอีกเครื่องมือเพื่อไม่ให้สถานะตีกัน
- แถบ Progress แสดงเฉพาะชื่อเครื่องมือกับเปอร์เซ็นต์ ข้อความขั้นตอนทำงานต้องแสดงในกล่อง Log และห้ามเขียนรายการเดิมซ้ำติดกัน

เครื่องมือและโมเดลที่ดาวน์โหลดต้องอยู่ใต้ `snapgen_data/tools` ไม่ควรคัดลอก
ไปไว้ใน `snapgen_modules`

## 9. Error log

ข้อผิดพลาดที่หลุดจาก callback หรือ background thread จะบันทึกที่:

```text
snapgen_data/logs/unhandled_errors.log
```

อย่ากลืน error สำคัญด้วย `except Exception: pass` หาก error นั้นทำให้งานของ
ผู้ใช้ไม่สำเร็จ ควรเขียน log หรือแสดงข้อความที่เข้าใจได้

## 10. ก่อนเผยแพร่เวอร์ชัน

ตรวจอย่างน้อย:

1. Python compile ผ่าน
2. `git diff --check` ผ่าน
3. Patch มี `manifest.json`
4. Patch ไม่มี `export`, cookies, accounts หรือข้อมูลใน `snapgen_data`
5. GitHub Release มี asset ชื่อ `tidmun-studio-patch.zip`
6. Restore เห็นเวอร์ชันใหม่จาก GitHub

คนละรอบของ GPT ยังเป็นเหตุการณ์เดียวกัน ไม่ใช่ปุ่มเลือกไฟล์ล่าสุด และไม่ใช่
ปุ่มเลือกรูปตัวละครจากคลังอ้างอิง

- รูปที่เลือกอาจเป็นภาพฉากก่อนหน้าภาพเดียว หรือ Storyboard คร่าวๆ หลายช่องของ
  ช่วงเหตุการณ์ก่อนหน้าก็ได้
- Prompt ที่ส่งต้องบอก GPT ให้อ่านภาพเหล่านี้เป็นประวัติเหตุการณ์ ทำความเข้าใจ
  ใครอยู่ที่ไหน เกิดอะไรขึ้น และสถานะล่าสุดของเรื่องคืออะไร
- ถ้าเป็น Storyboard ให้ไล่อ่านตามลำดับช่องและใช้ช่องสุดท้ายที่เกี่ยวข้องเป็น
  สถานะล่าสุด ห้ามสร้างตาราง Storyboard ซ้ำหรือรวมทุกเหตุการณ์เป็นภาพเดียว
- เมื่อผู้ใช้เลือกไฟล์ ต้องส่งภาพผ่าน Vision เข้าแชทเรื่องเดิมทันที พร้อมคำสั่ง
  `ยังไม่ต้องสร้างภาพ` และรอรับ `conversation_id` กับ `parent_message_id`
- เมื่อ GPT รับรู้บริบทแล้ว ห้ามแนบ Storyboard/ภาพเหตุการณ์ก้อนเดิมซ้ำในคำขอ
  สร้างภาพ เพราะจะตีกับรูปตัวละครและรูปอ้างอิง
- ถ้าส่งบริบทไม่สำเร็จ ต้องแจ้งใน Log และห้ามแสดงสถานะว่าพร้อม
- รูปตัวละครและสถานที่ที่จับคู่จากชื่อ Prompt ยังส่งร่วมกันได้
- ให้รักษาสถานที่ ตัวละคร เสื้อผ้า พร็อพ เวลา แสง และสภาพของเหตุการณ์เดิม
- เปลี่ยนสถานที่หรือรายละเอียดเดิมได้เมื่อ Prompt ใหม่สั่งอย่างชัดเจนเท่านั้น
- ห้ามนำปุ่ม `ล่าสุด` กลับมา เพราะการเดาไฟล์ล่าสุดอาจเลือกภาพผิดเหตุการณ์

### กฎประวัติของหน้า Image AI

- ทุกคำขอจากหน้า `สร้างรูป AI` ต้องใช้ประวัติ GPT เดิม ทั้งการสร้างปกติ,
  Storyboard และ Auto-Gen
- การสลับหน้า ปิดโปรแกรม แล้วเปิดใหม่ ต้องกลับมาใช้ประวัติเดิม รหัสประวัติ
  จึงบันทึกไว้ใน `snapgen_data/meta/image_story_conversation.json`
- ไฟล์นี้เก็บเฉพาะ `conversation_id` และ `parent_message_id` ไม่เก็บ Prompt,
  ข้อความตอบ รูป หรือเสียง
- มีเพียงปุ่ม `เริ่มประวัติใหม่` ในหน้า Image AI ที่มีสิทธิ์ล้างรหัสประวัตินี้
- ช่องชื่อเรื่องหน้า Image แสดงชื่อได้ต่อเมื่อบทฉบับปัจจุบันถูกส่งสำเร็จและมีทั้ง `conversation_id`, `parent_message_id` และ hash บทตรงกัน; Context อย่างเดียวห้ามทำให้ชื่อขึ้น
- หน้า Ref, Prop, Story Face, สล็อตวิดีโอ และหน้าอื่น ห้ามอ่านหรือเขียนประวัติ
  ของหน้า Image AI แม้ทุกหน้าจะใช้ระบบสร้างรูปส่วนกลางตัวเดียวกัน

### กฎประวัติของหน้า Ref

- หน้า Ref อ่านบทต้นฉบับเดียวกับ Prompt-Ref จาก `snapgen_data/prompt_ref_source.txt` แต่ใช้ประวัติ GPT แยกที่ `snapgen_data/meta/ref_story_conversation.json`
- ห้ามใช้ cursor เดียวกับ Prompt-Ref หรือ Image AI เพราะงานแตกฉาก งานสร้างภาพต่อเนื่อง และงานออกแบบ Ref ต้องไม่ปนกัน
- ก่อนสร้าง Ref ต้องกด `เริ่มประวัติใหม่` ให้ GPT หน้า Ref อ่านบทฉบับปัจจุบันสำเร็จก่อน
- ช่องชื่อเรื่องหน้า Ref ต้องว่างจนกว่าจะส่งบทสำเร็จและได้ `conversation_id`, `parent_message_id` พร้อม hash บทที่ตรงกับไฟล์ปัจจุบัน
- เมื่ออัปโหลดบทใหม่ ล้างบท หรือเริ่มเรื่องใหม่ใน Prompt-Ref ให้ล้างสถานะชื่อและประวัติ Image/Ref ทันที แม้ Context ใหม่จะมีชื่อเรื่องแล้วก็ตาม
- Ref ปกติ, Auto ตัวละคร และ Auto สถานที่ต้องใช้ประวัติ Ref เดิมจนกว่าจะเริ่มประวัติใหม่

## 12. บทบาทของรูปแนบในหน้า Image

### PBR AI ของหน้า Prop

- ปุ่ม `สร้าง PBR` ในการ์ด Texture ใช้ `StableNormal-turbo` สร้าง Normal ด้วย AI; ห้ามย้อนกลับไปใช้ความสว่างของ Base Color สร้าง Normal แบบตรงๆ เพราะแสงและสีไม่ใช่รูปทรงผิว.
- StableNormal ติดตั้งแยกใน `snapgen_data/tools/stable_normal` และดาวน์โหลดอัตโนมัติครั้งแรก ห้ามติดตั้ง PyTorch ลง `.venv312` ของโปรแกรมหลัก.
- Roughness ต้องมีรายละเอียดแปรผันตามผิวและยึดค่ากลางตามชนิดวัสดุ ห้ามสร้างเป็นสีเทาค่าเดียวทั้งภาพ.
- Metallic เป็นสมบัติวัสดุ: ผ้า ไม้ หิน หนัง และพลาสติกต้องเป็น 0 (ดำ); เฉพาะชนิด `โลหะ` เป็น 1 (ขาว). ภาพดำจึงไม่ใช่ข้อผิดพลาดเมื่อวัสดุไม่ใช่โลหะ.
- Base Color, Normal และ Roughness ต้องรักษาขอบซ้าย/ขวาและบน/ล่างให้ต่อกันได้ก่อนนำไป Tiling.

### กฎสีปุ่มประวัติ

- ปุ่ม `เริ่มประวัติใหม่`, `เริ่มเรื่องใหม่` และ `เปลี่ยนเรื่อง` ทุกหน้าใช้สี `HISTORY` เท่านั้น: พื้นขาวอมฟ้า `#EFF6FF`, ตัวอักษรน้ำเงินเทา `#315A75`, ตอนกด `#DBEAFE` และขอบ `#BFDBFE`.
- สี `HISTORY` สงวนให้การเริ่มหรือเปลี่ยนประวัติ GPT ห้ามนำไปใช้กับ Select, Auto, แนบไฟล์, สร้าง, ล้าง หรือเครื่องมือทั่วไป.
- เพิ่มหน้าหรือย้ายปุ่มภายหลัง ให้เรียก `STYLE.HISTORY` จาก `snapgen_button_styles.py`; ห้ามกำหนดสีใหม่เฉพาะหน้า.

เวลาแนบหลายรูปพร้อมกัน ห้ามส่งเป็นกองรูปที่ไม่มีคำอธิบาย เพราะ GPT อาจเอาหน้าที่
ของแต่ละรูปไปปนกัน เช่น เอาเสื้อผ้าจากรูปตัวละครไปทับฉากปัจจุบัน หรือให้ storyboard
ไปเปลี่ยนสถานที่ของเหตุการณ์

ลำดับและหน้าที่ที่ต้องรักษา:

1. รูปจากปุ่ม `📎 ต่อจากฉากก่อน` = ส่งเป็น Vision turn ก่อนสร้างภาพและเก็บไว้ในประวัติ ไม่ส่งซ้ำในคำขอสร้าง
2. รูปฉากที่ Auto-Gen สร้างก่อนหน้า = ตัวคุมความต่อเนื่องหลักของรอบ Auto-Gen
3. รูปตัวละคร/สถานที่จากคลังอ้างอิง = ใช้เฉพาะตัวตน หน้าตา รูปร่าง หรือรายละเอียดชื่อที่ตรงกับ Prompt
4. รูป Storyboard ที่ Auto-Gen สร้างเอง = ใช้เป็นแผนภาพรวมเท่านั้น ห้ามทับฉากก่อนหน้าหรือ Prompt ปัจจุบัน

ถ้ารูปเกินขีดจำกัด 10 รูป ให้รักษารูปฉากก่อนหน้าและรูปอ้างอิงที่ตรงกับ Prompt
ก่อนรูป Storyboard เสมอ

### กฎประวัติ Prompt-Ref

- Prompt-Ref ใช้หนึ่งแชท GPT ต่อหนึ่งเรื่อง แยกจากประวัติหน้า Image AI
- ครั้งแรกปุ่มหลักชื่อ `เริ่มเรื่องจากบทนี้`; GPT อ่านบททั้งเรื่องก่อนและยังไม่แตก Prompt
- บททั้งเรื่องต้องส่งเป็นไฟล์แนบ UTF-8 (`prompt_ref_full_story.txt`) ผ่านระบบ file upload ของ Bridge ไม่ยัดบทเป็นข้อความก้อนใหญ่ เพราะบทอาจยาวเกินข้อความที่ส่งครบ
- หลัง GPT อ่านบท โปรแกรมต้องสั่งสร้าง Prompt-Ref Context เป็นข้อความถัดไปในประวัติเดียวกัน แล้วบันทึกให้หน้า Ref/Prop ใช้
- ส่งบทสำเร็จแล้วปุ่มหลักเปลี่ยนเป็น `แตกฉากนี้`; ช่องเดิมใช้วางฉากปัจจุบัน
- หลังส่งสำเร็จ ช่องเดิมใช้วางฉากปัจจุบัน ทุกครั้งที่กด `AI แตก Prompt` ต้องต่อจากประวัติเดิม
- เก็บเฉพาะ `conversation_id` และ `parent_message_id` ที่ `snapgen_data/meta/prompt_ref_conversation.json`
- มีเพียงปุ่ม `เริ่มเรื่องใหม่` ที่ล้างประวัติ Prompt-Ref
- ห้ามส่ง Context เก่าซ้ำทุกฉาก เพราะบททั้งเรื่องอยู่ในประวัติแล้ว
- ประวัติ Prompt-Ref ห้ามใช้ร่วมกับหน้า Image AI, Ref, Prop, Story Face หรือสล็อตวิดีโอ
- ปุ่ม Save บันทึกได้เฉพาะ prompt bank ห้ามเขียนผลลัพธ์ Slot ทับ Context
- ปุ่ม `Prompt-Ref Context` ต้องอยู่ต่อ เพราะใช้จัดทำข้อมูลกลางสำหรับหน้า Ref, Prop และหน้าอื่น; ระบบประวัติ Prompt-Ref ใหม่ห้ามลบหรือแทนที่ปุ่มนี้
- ปุ่ม `อัปเดต Context ในประวัติเดิม` ต้องต่อจาก conversation cursor เดียวกัน ห้ามเปิดแชท GPT ใหม่
- Prompt-Ref ต้องทำ Clip Contract ก่อนทุก Slot: สิ่งที่เกิดแล้ว, ขอบเขตคลิปนี้, สิ่งที่เก็บไว้ทีหลัง, เฟรมเริ่ม และเฟรมจบ
- บันทึก Clip Contract ล่าสุดที่ `snapgen_data/prompt_ref_last_clip_contracts.json`; ไม่ต้องเพิ่มปุ่มหรือกล่องใหม่ใน UI
- รูปอ้างอิงแต่ละรูปต้องมีหน้าที่หลักเดียว เช่น identity, environment หรือ previous-event continuity และห้ามถ่ายโอนรายละเอียดนอกหน้าที่

## 13. ระบบไมค์ต้องรองรับหลายเครื่อง

SnapGen ไม่ได้ออกแบบมาสำหรับคอมเครื่องเดียว ห้ามเขียนค่าผูกกับชื่อการ์ดจอหรือ
สเปกของเครื่องใดเครื่องหนึ่งโดยตรง

- ระบบถอดเสียงใช้ Whisper `large-v3` รุ่นเดียวทุกเครื่อง ไม่มีตัวเลือกรุ่นอื่น; ถ้ายังไม่มีให้ดาวน์โหลดอัตโนมัติเมื่อกดไมค์ และเลือก GPU ก่อนแล้ว fallback เป็น CPU
- ตอนเริ่มใช้ ให้ลอง CUDA GPU ก่อน (`float16`) เพื่อความเร็ว
- ถ้าไม่มี NVIDIA GPU, ไดรเวอร์ไม่พร้อม, หรือ CUDA ใช้ไม่ได้ ต้องสลับเป็น CPU
  (`int8`) เองและยังต้องใช้งานได้ ไม่ให้ปุ่มไมค์พัง
- โมเดลจะดาวน์โหลดครั้งแรกต่อเครื่อง แล้วเก็บไว้ใช้ซ้ำในเครื่องนั้น
- ห้ามเดาว่าทุกเครื่องเป็น RTX 4060 Ti หรือมี GPU; ให้ตรวจจากการเปิดโมเดลจริง
- Settings ต้องแสดงโมเดลที่ดาวน์โหลดอยู่ในเครื่องนั้นพร้อมขนาด และให้ดาวน์โหลด
  หรือลบเป็นรายรุ่นได้ การลบต้องถามยืนยันก่อนเสมอ
- ปุ่มไมค์ต้องเขียน log อย่างน้อยเมื่อเริ่มอัด หยุดอัด โหลดโมเดล เลือก GPU/CPU
  ถอดข้อความสำเร็จ หรือเกิดข้อผิดพลาด

## 14. บล็อกควบคุมกล้องในหน้า Image

บล็อก `ควบคุมกล้อง` ต้องอยู่ด้านขวาภายในกรอบ Prompt แยกจากแถวปุ่มสร้างรูป
เพื่อไม่ให้เครื่องมือหลักด้านล่างรก

- มีเพียง `อัตโนมัติ`, `เน้นหน้า`, `เน้นตัวละคร`, `เน้นฉาก`
- เลือกได้ครั้งละหนึ่งค่าและต้องเห็นสีของค่าที่เลือก
- ห้ามเขียนข้อความควบคุมกล้องลงในช่อง Prompt ให้ผู้ใช้เห็นหรือสะสมซ้ำ
- เติมคำสั่งกล้องเฉพาะตอนส่งสร้างรูปแบบ Manual
- Storyboard และ Auto-Gen ใช้มุมกล้องจาก Prompt ของแต่ละฉากเอง
- คำสั่งกล้องเปลี่ยนเฉพาะการจัดภาพ ห้ามเปลี่ยนตัวละคร เสื้อผ้า สถานที่ หรือเหตุการณ์

## 15. กฎข้อความหน้าต่างดำตอนเปิดโปรแกรม

- ตอนเปิดปกติให้แสดงเพียง `[SnapGen] พร้อมใช้งาน ✓` หนึ่งบรรทัด
- ห้ามเพิ่มข้อความติดตั้งโมดูล ปุ่ม ระบบย่อย Bridge หรือสถานะสำเร็จทั่วไปลงหน้าต่างดำ
- รายละเอียดสำหรับตรวจบัคใช้ `_snapgen_startup_detail(...)` เท่านั้น และจะแสดงเมื่อกำหนด `SNAPGEN_VERBOSE_STARTUP=1`
- Error, Warning และ traceback จริงต้องแสดงเสมอ ห้ามซ่อน เพราะใช้หาสาเหตุเมื่อโปรแกรมเปิดไม่ได้

## 16. กฎขนาดปุ่มทุกหน้า

- ปุ่มคำสั่งหลักทุกหน้าใช้ขนาดเดียวจาก `snapgen_modules/snapgen_button_styles.py`: `width=14`, `height=1`, `padx=14`, `pady=7` และฟอนต์ UI กลางจาก `snapgen_modules/snapgen_fonts.py`
- ปุ่มคำสั่งที่อยู่แถวหรือชุดเดียวกันต้องกว้างและสูงเท่ากัน ห้ามกำหนดขนาดเฉพาะหน้าเอง
- ถ้าข้อความยาว ให้ปรับถ้อยคำให้สั้นก่อน ห้ามขยายปุ่มเพียงปุ่มเดียวจนแถวไม่เท่ากัน
- ยกเว้นเฉพาะปุ่มจิ๋วที่มีหน้าที่ชัดเจน เช่น `X`, ไมค์, ลูกศร, Slot และปุ่มในการ์ด Gallery
- สีเปลี่ยนตามหน้าที่ได้ แต่ขนาดปุ่มคำสั่งหลักต้องเท่ากันทุกหน้า
- ช่องแสดงการทำงานของหน้าหลักต้องใช้รูปแบบเดียวกันทุกหน้า; ถ้าหน้าอื่นไม่มีหัวข้อ `Log` ห้ามเพิ่มคำว่า `Log` เฉพาะหน้าใดหน้าหนึ่ง

## 19. กฎใบหน้าตัวละครเดียวกันต่างวัย

- หน้านิทานหาและแนบหน้าเดิมหลังบ้านอัตโนมัติเพื่อสร้างคนเดิมในวัยอื่น รูปนี้คุมเฉพาะ identity ของใบหน้า; ห้ามเพิ่ม dropdown `หน้าเดิม` ให้ผู้ใช้เลือกเองจนหน้าจอรก
- ต้องรักษารูปหน้า ระยะตา คิ้ว จมูก ปาก กราม โหนกแก้ม หู สีผิว และตำหนิเด่น แต่เปลี่ยนริ้วรอย ความตึงผิว ไขมันใบหน้า และเส้นผมตามวัยเป้าหมาย
- ห้ามคัดลอกอายุ เสื้อผ้า ฉาก แสง ท่า หรือสีหน้าจากรูปอ้างอิง และผลลัพธ์ต้องมีคนเดียว
- งาน `ข้อมูลชุด` ที่มีชื่อเดียวกันหลายวัยต้องใช้รูปแรกของคนนั้นเป็น identity reference ให้รูปวัยถัดไปอัตโนมัติ
- เมื่อกด `Select` ต้องหารูปที่สร้างแล้วของคนชื่อเดียวกันอัตโนมัติ รวมช่วงวัยและสถานะอารมณ์ เช่น ปกติ เครียด เศร้า หรือแก่ แล้วแนบตอนสร้างโดยไม่ให้ผู้ใช้เลือกเอง
- ชุดข้อมูลที่ GPT แยกต้องมี `identity_group`, `identity_master`, `reference_from`: คนเดียวกันทุกวัย/อารมณ์ใช้ group เดียวกัน, มี master เพียงหนึ่งรูปและสร้างก่อน, ตัวแปรอื่นอ้าง group ของ master; การตัดคำจากชื่อใช้เป็น fallback สำหรับข้อมูลเก่าเท่านั้น
- ปุ่ม `Select` หน้านิทานห้ามเรียก GPT, Bridge หรือ network บน UI thread; ใช้เฉพาะ Prompt Context และผล `วิเคราะห์` ที่บันทึกแล้ว งานวิเคราะห์ใหม่ทำได้จากปุ่ม `วิเคราะห์` ใน worker thread เท่านั้น เพื่อไม่ให้หน้าหลักค้าง
- รูปหลักคุมเพียง identity; ช่วงชีวิต สภาพชีวิต สุขภาพ สภาพร่างกาย น้ำหนัก ความโทรม การอดนอน ความเครียด สีหน้า ดวงตา ผิวและการดูแลตัวเองจากตัวละครเป้าหมายต้องมี priority สูงกว่า condition ของรูปหลัก และต้องเห็นความต่างชัด
- กล่อง `ซ่อม UV Texture` หน้านิทานส่งไฟล์เป็น image edit แยกจาก Face prompt, ล็อก canvas/pixel registration/UV islands/landmarks และบันทึกไฟล์ใหม่ใน `export/story_face/uv_repair`; ห้ามทับต้นฉบับ และต้องคืนขนาดพิกเซลเท่าต้นฉบับ หลัง GPT ต้อง composite พื้นหลัง ขอบ island และกลางหน้าที่มีตา/จมูก/ปากจากต้นฉบับกลับเพื่อกัน UV และ identity เลื่อน
- งานซ่อมผม UV ต้องสร้าง `short dense hair cap` เป็นก้อนมวลผมสีเข้มเต็มเกาะ scalp ก่อน เส้นสั้นใช้เป็นรายละเอียดบางๆ เท่านั้น ห้ามผมยาว เส้นขาวถี่ รูสีเนื้อหรือขอบแหว่ง; post-process ต้องปิดรูสว่างภายในมวลผมโดยไม่กินหน้าผาก
- กล่อง `ชุดตัวละคร 3D` ต้องอยู่หน้านิทาน ไม่ใช่หน้า Prop: GPT ออกแบบชุดคู่จาก Story + Character Context แล้วสร้างรูปแยก `เสื้อ` และ `ท่อนล่าง` ใน Gallery นิทาน ทั้งคู่ใช้ outfit_id เดียวกัน; แต่ละการ์ดมี `ส่งไป Prop` เพื่อแนบรูป ตั้งชื่อ และสลับหน้า Prop เมื่อต้องการสร้าง 3D ห้ามวางกล่องออกแบบชุดซ้ำในหน้า Prop
- dropdown ชุดตัวละคร 3D ต้องอ่านเฉพาะ `story_face_batch_latest.json` / `batch_cache` จากปุ่ม `ข้อมูลชุด → วิเคราะห์` ของนิทาน ห้ามอ่าน `_load_ref_context()` หรือ `prompt_ref_context.json` เพราะเป็นตัวละครของหนัง AI คนละระบบ
- รูป `เสื้อ` จากชุดตัวละคร 3D ต้องเป็น volumetric ghost-mannequin T-pose: หุ่นล่องหนค้ำให้เห็นอก หลัง ไหล่ รอบลำตัว แขนทรงกระบอก ปก ช่องแขนและชายเสื้อมีความลึก แต่ห้ามเห็นหุ่นหรือผิว แขนกางแนวนอนเป็นตัว T ใช้มุมเฉียงหน้าประมาณ 15° เพื่อเห็นความหนา ห้าม flat-lay แผ่นผ้าแบน เสื้อพับ ไม้แขวน A-pose แขนตก/งอ/เฉียง; ท่อนล่างต้องมีปริมาตรเอว สะโพก ก้นและขาจาก ghost form เช่นกัน
- แถบ 3D เป็นแถบร่วมของ TripoSplat/TRELLIS.2: เมื่อเลือกรูปใหม่หรือกดเริ่มงาน ต้อง set และวาด `0%` ทันทีบน UI thread ก่อนเปิด worker ห้ามปล่อยค่า `100%` จากงานก่อนค้างอยู่
- TRELLIS.2 local ใช้ upstream quality pipeline `resolution=1024`, texture `4096`, mesh target `300k`; ห้ามลดกลับเป็น 512/2048 เพื่อประหยัด VRAM โดยไม่บอกผู้ใช้
- TripoSplat บนเว็บแสดง native Gaussian/Splat ซึ่งละเอียดกว่า mesh conversion; โปรแกรมต้องเก็บ `source.splat`/`source.ply` เป็นผลต้นฉบับเสมอ และห้ามอ้างว่า GLB/FBX ที่แปลงจาก Splat จะเหมือน viewer เว็บทุกประการ
### Blender clothes fitting

- หน้า `นิทาน` เป็นเจ้าของปุ่ม `แก้เสื้อผ้าใน Blender`; อย่าย้ายไปหน้า Prop เพราะเป็นงานชุดตัวละคร 3D.
- ปุ่มส่งคำสั่งผ่านไฟล์ IPC ใน `%LOCALAPPDATA%/SnapGen/blender_clothes_fit` เท่านั้น ไม่รับคำสั่งจากเครือข่าย.
- ผู้ใช้ต้องเลือก Body ก่อน แล้ว Shift+เลือกเสื้อผ้าเป็น Active object ชิ้นสุดท้าย รวม 2 Mesh เท่านั้น.
- แก้เฉพาะ vertex ของเสื้อผ้าที่จมหรือชิด Body ด้วย Shrinkwrap `OUTSIDE_SURFACE`; ห้ามดึงเสื้อทั้งชิ้นแนบ Body.
- น้ำหนัก Conform ต้องไล่แบบ Smoothstep จากจุดทะลุ 100% ไปขอบ 0% ภายใน 15 มม. ห้ามใช้ Vertex Group แบบตัด 0/1 เพราะทำให้ผ้าหักเป็นขอบ.
- หลัง Shrinkwrap ใช้ Smooth เบาๆ เฉพาะกลุ่มเดียวกัน (`factor 0.12`, `2 iterations`) เพื่อเกลี่ยรอยต่อ แต่ห้ามลบรอยพับทั้งชุดหรือเพิ่ม Subdivision โดยไม่จำเป็น.
- ชนิด 3D มาจากข้อมูลที่หน้า `นิทาน` สร้างไว้แล้ว ห้ามให้ผู้ใช้เลือกซ้ำตอนแก้ใน Blender.
- ส่งชนิดจาก `นิทาน → Prop → Hunyuan/TripoSplat/TRELLIS.2` และตั้งชื่อตอนสร้าง 3D เสร็จทันที.
- ชื่อไฟล์, Object และ Mesh data ต้องเป็นชนิดอังกฤษ: `Shirt`, `Pants`, `Skirt`, `Dress`; ห้ามปล่อย `node_*`, `model` หรือ `prop` สำหรับงานชุดนิทาน.
- เก็บผลเป็น Modifier `SnapGen Fit Above Body` เพื่อย้อนกลับได้; ห้าม Apply หรือ Save ไฟล์ Blender อัตโนมัติ.
- ทุกครั้งต้องรายงานชื่อ Body, ชื่อเสื้อผ้าใหม่, จำนวนจุด และข้อผิดพลาดใน Log หน้า `นิทาน`.

## 20. กฎปุ่มเปิดโฟลเดอร์มุมขวาบน

- ถ้าหน้า `ตัดเสียง` ยังไม่มีไฟล์ล่าสุด หรือผู้ใช้กด `ล้าง` แล้ว ให้เปิด `export/audio` เป็น fallback

## 21. เครื่องมือแก้ปุ่มส่วนตัว

- คีย์ลัด `Ctrl+Shift+E` เข้าโหมดเลือกปุ่มบนหน้าจอจริง; ปุ่มที่แก้ได้ต้องมีกรอบฟ้าและ cursor แบบเลือก จากนั้นคลิกปุ่มเพื่อเปิดตัวแก้รายปุ่มทันที
- ระหว่างโหมดแก้ไข command เดิมของปุ่มต้องไม่ทำงาน เช่น คลิก `ล้าง` ต้องเปิดตัวแก้และห้ามล้างข้อมูล; กด `Esc` หรือกด `Ctrl+Shift+E` ซ้ำเพื่อยกเลิก
- `Ctrl+Shift+C` เดิมยังใช้เปลี่ยนสีตามประเภทแบบชั่วคราว
- แก้ได้เฉพาะชื่อ สี ความกว้าง ความสูง และลำดับภายใน parent/แถวเดิม ห้ามเปลี่ยน command หรือย้ายข้ามหน้า
- การย้ายใช้ `ย้ายซ้าย` / `ย้ายขวา` ไม่ใช้ลากอิสระ เพราะ Tkinter pack/grid อาจพังเมื่อย้ายข้าม container
- กด `บันทึก` ต้องเก็บใน `ui_button_edits` ผ่าน config และคืนค่าหลังเปิดโปรแกรมใหม่
- ชื่อ สี ความกว้างและความสูงต้อง preview บนปุ่มจริงทันทีขณะแก้; `บันทึก` มีไว้ยืนยันและเก็บข้ามการเปิดโปรแกรม
- ปิดหน้าต่างแก้ด้วย X โดยไม่บันทึก ต้องย้อนค่าชั่วคราวและตำแหน่งกลับก่อนแก้
- มี `คืนค่า` รายปุ่มและต้องคืนค่าต้นฉบับจากโค้ดทันที รวมชื่อ สี ขนาด และตำแหน่ง โดยไม่ต้องรีสตาร์ต

## 22. รายงาน Error จากทุกเครื่อง

- ทุกเครื่องใช้ `snapgen_error_reporter.py` ส่ง Error ที่กรองข้อมูลแล้วเป็น GitHub Issue กลาง ห้าม commit ไฟล์ log ลง repository
- รายงานมีรหัสเครื่องแบบสุ่ม, รุ่นโปรแกรม, Windows, Python, CPU, RAM, GPU, จุดที่พังและ traceback ที่กรองแล้ว
- ห้ามส่ง prompt, รูป, เสียง, export, cookie, token, API key, email, ชื่อ Windows user หรือ path ผู้ใช้จริง
- Error fingerprint เดียวกันต้อง comment รวม Issue เดิม ห้ามสร้าง Issue ซ้ำรัวๆ
- เครื่องไม่มีเน็ตหรือยังไม่ Login `gh` ต้องเก็บคิวใน `snapgen_data/error_reports` และลองส่งภายหลัง ห้ามทำให้งานหลักรอหรือพัง
- ผู้ใช้เครื่องทีมไม่ต้องรู้จัก Git, log, commit หรือ push: ถ้ายังไม่ยืนยันบัญชี โปรแกรมเปิด browser authorization ให้ครั้งเดียว แล้วส่งคิวเองหลังยืนยันสำเร็จ
- Log ทุกหน้าที่มี ERROR/FAILED/Exception/ล้มเหลว/ไม่สำเร็จต้องเข้าระบบกลาง รวม Video, Image, Ref, Prop, นิทาน, คาราโอเกะ และตัดเสียง
- ต้องจับ startup/runtime console, unhandled GUI/thread exception, Python fatal crash, โปรแกรมปิดไม่สมบูรณ์ครั้งก่อน และ UI ค้างเกิน 45 วินาที พร้อม thread stack
- Session sentinel ต้องเขียน heartbeat แบบเบาทุก 2 วินาทีและทำเครื่องหมาย clean ตอนปิดปกติ; ถ้าเครื่องดับ/process crash ให้รายงานเมื่อเปิดครั้งถัดไป
- Prompt-Ref ต้องอ่าน conversation cursor ได้ทั้ง response layout ใหม่/เก่า; ถ้า Bridge เครื่องผู้ใช้ไม่คืน cursor ให้ refresh source โดยรักษา secrets/accounts, patch, restart และ retry เฉพาะ Context upload หนึ่งครั้ง ห้ามให้ผู้ใช้รีสตาร์ต Bridge เอง และห้ามใช้ retry นี้กับงานสร้างภาพ
- ประวัติ Prompt-Ref ต้องผูกกับ SHA-256 ของบทที่อัปจริง: ถ้าผู้ใช้เลือก/แก้ไฟล์ใหม่ ห้ามใช้ cursor เก่าแม้ cursor ยังอยู่ ต้องอัปบทใหม่ก่อนสร้าง Context เพื่อกัน GPT ตอบจากเรื่องเก่า
- Prompt-Ref ต้องส่งเนื้อหาไทยเป็น `input_text` แบ่งส่วนใน turn แรกจนได้ `STORY_READY` แล้วจึงแนบไฟล์ต้นฉบับใน turn ที่สองของประวัติเดิม เพราะ ChatGPT Web file parser บางเครื่องแปลง UTF-8 ไทยเป็น `????`; ห้ามส่งไฟล์พร้อมข้อความหลักใน turn เดียวและห้ามให้ผลอ่านไฟล์ทับ FULL_STORY_PART
